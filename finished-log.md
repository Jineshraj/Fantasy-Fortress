## 0. Rules that governed the work

These came from the spec and were treated as non-negotiable throughout:

- Existing data stays real. Unavailable fields render `—`, `Not available`, or `Breakdown pending` — never a guessed value.
- `final_points` is the total authority. The UI must never sum a local ledger to produce a total.
- `points_breakdown` is generated by the scoring engine (server), never by a second algorithm in React.
- If the stored breakdown does not reconcile exactly with the approved base total, the server publishes `available: false` and the client falls back to `Base points (server)` + `Breakdown pending`. An unknown aggregate is never labelled `Bonus`.
- Gold `[ C ]` badge only when `multiplier === 2`. Silver `[ VC ]` for the submitted vice. The original captain loses the gold badge after handover (`handedOver`). If neither played, no 2x badge.
- Display states are `STARTER | AUTO_SUB_OUT | AUTO_SUB_IN | BENCH_UNUSED`, driven only by stored `role` / `is_effective_starter`. A bench player never moves onto the pitch.
- `fetchTeamSquad` must not fall back to another gameweek — an explicit empty state instead.
- Fixture ids are stable (`match_id` or row UUID). Broadcast codes come from an explicit `CLUB_BROADCAST_CODES` map with a `—` fallback, never a 3-letter string compare. Fixture scores stay visible alongside status labels.
- No headless browser in the repo, so there is no automated `scrollWidth` overflow assertion. Overflow was verified with `scale-check.mjs` plus manual review.

## 10. Server — scoring engine, rule table, persistence

### 10.1 `server/src/services/scoringRules.js` *(new, 198 lines)*

Single source of truth for the point rules. Three exports:

- `buildPointsBreakdownItems(stats, fantasyPos)` — itemized ledger in spec display order. Accepts staging keys (`clean_sheet`, `pen_miss`, `pen_save`) and engine detail keys (`isCS`, `penMiss`, `penSave`). Accepts fantasy codes `GKP/DEF/MID/FWD` and provider short codes `G/D/M`.
- `calculatePlayerPoints(stats, fantasyPos)` — literally the sum of those items, so total and ledger cannot drift apart.
- `buildPointsBreakdown(stats, fantasyPos, basePts)` — publishes `{available: true, items}` **only** when the sum equals `basePts`; otherwise `{available: false, items: []}`.
- `buildMatchBreakdown(detail, { position, gameweek })` — per-fixture `PlayerMatch[]` from the engine’s `detail.matches`. Returns `null` when no per-fixture source rows exist. `stadiumBonus` is forced to `0` and `multiplier` to `1` because both apply at gameweek level, not per fixture.

### 10.2 `sofaScoreSyncService.js`

The local `calculatePlayerPoints` implementation (~55 lines) was removed and replaced with:

```js
import { buildPointsBreakdownItems, calculatePlayerPoints } from './scoringRules.js'
export { buildPointsBreakdownItems, calculatePlayerPoints }
```

Existing import paths in `dashboardService.js` and `scripts/checkStagingDrift.js` keep working unchanged.

### 10.3 `scoringEngine.js` (+81 lines)

- `matchInfoById` fixture objects now carry `fixtureId` (canonical `sofaId || afId || gw_home_away`, matching `supabaseSyncService`’s `fixtures.match_id`), `homeScore`, `awayScore`.
- New `buildMatchRec(source, matchId, club, ev)` — resolves a staging row’s fixture, derives `venue` with a two-sided `matchHomeClub` check, and sets `opponentName`.
- New `pushMatchRec(map, pName, rec)` — keeps a de-duplicated per-fixture list on the aggregate stats object. Staging is already one row per (player, match); the aggregate maps previously flattened them.
- Both staging loops (`SofaScore_Staging`, `API_Football_Staging`) now populate the per-fixture list.
- The fabricated fallback detail gained `matches: []`.
- Both `scoredPlayers.push(...)` sites (effective XI at L1019, bench/subbed at L1055) emit:
  ```js
  points_breakdown: buildPointsBreakdown(detail, p.position, pData.pts),
  match_breakdown:  buildMatchBreakdown(detail, { position: p.position, gameweek: targetGw }),
  ```

### 10.4 `supabaseSyncService.js` (+5 lines)
